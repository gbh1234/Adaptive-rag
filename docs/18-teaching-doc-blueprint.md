# 项目教学文档写作思路（技术主线 · 12 部分细化版）

> 本文是**教学文档的施工图**：先定定位，再给技术主线结构、12 部分章节大纲（含代码锚点）、每章模板、写作规范与推进节奏。
>
> **本版核心**：章节按**技术主题**组织，并**按难度循序渐进**（基础 → 进阶 → 决策 → 控风险 → 验证 → 上线）。共 **12 个部分 · 19 章**。
>
> **测评仍是独立部分**（不埋进工程保障），但**放在技术讲完之后**作为"验证"环节，不打断技术的递进。
>
> 第 1 章 = 项目总介绍 + 简历写法 + 3 分钟自述。

---

## 0. 为什么用"技术主线"

按 `app/` 目录写是**代码视角**，读者学到"这个项目长什么样"；按技术主题写是**能力视角**，读者学到"向量怎么做、召回怎么选、记忆怎么管"。

| | 项目/代码主线 | 技术主线（本版） |
|---|---|---|
| 组织单位 | 模块、文件、请求链路 | 技术点：向量 / 召回 / 上下文 / 记忆…… |
| 可迁移性 | 低（换项目即失效） | 高（技术能带到任何 RAG 项目） |
| 面试价值 | 中（只能讲本项目） | 高（先答通用八股，再落回本项目） |
| 风险 | 变成目录导读 | 需用本项目做真实锚点，避免空谈理论 |

**原则**：技术当骨架，本项目当血肉，评测当证据。

---

## 1. 技术的循序渐进：六个阶段

技术主线不能是"知识点罗列"，必须**由浅入深**。读者的认知路径是：先知道"数据怎么进来、怎么被找到"，再知道"怎么找得更准"，然后才是"怎么决策、怎么执行、怎么控风险"，最后才是"怎么证明有效、怎么上线"。

因此把 12 个部分归入 **6 个递进阶段**：

| 阶段 | 回答的问题 | 包含部分 |
|---|---|---|
| 一 · 打基础 | 知识怎么变成可检索的数据？ | 向量表示、索引构建、召回 |
| 二 · 提质量 | 怎么让检索更准、上下文更有效？ | 融合精排、查询改写 |
| 三 · 管上下文 | 怎么喂给模型、怎么保持会话？ | 上下文与记忆 |
| 四 · 做决策 | 走哪条路、怎么编排、怎么调工具？ | 意图与路由、工作流与工具 |
| 五 · 控风险 | 高风险动作怎么挡？ | 安全护栏 |
| 六 · 拿证据 · 上生产 | 怎么证明有效？怎么上线？ | 评测体系、工程化与上线 |

**两条排序纪律**：
1. **部分之间**：只有前面阶段讲完，后面的阶段才有前提。比如不先讲召回，就讲不了 RRF 融合。
2. **部分之内**：章节也从"是什么"到"怎么用"再到"坑在哪"，不跳步。

**评测的位置**：它回答的是"这一整套东西到底有没有用"，**必须等技术全部讲完才成立**——所以放在第六阶段（验证），而不是插在前面。这样既不突兀，又保持了"独立成部分"的分量。

## 3. 章节大纲（12 部分 · 19 章，含代码锚点）

> 每章统一产出：**概念要点 → 本仓库实现（代码锚点）→ 为什么（取舍 + 反例）→ 练习 → 指标回指**。

### 第一部分 · 项目总览（第 1 章）

**第 1 章 项目总介绍、简历写法与 3 分钟自述**
- **1.1 业务背景与核心问题**：传统客服 RAG 只有一条链路；四类问题（FAQ / 订单 / 复杂售后 / 写操作）对延迟、召回、风险要求不同。锚点：`README.md`、`docs/01-overview.md`
- **1.2 一句话 / 30 秒版本**：可背模板
- **1.3 3 分钟自述稿**：五段式——业务背景 → 核心问题 → 解决方案 → 工程保障 → 结果（带指标）
- **1.4 指标引子**：一张表摆出最硬的数字，但只点到为止，**完整口径留到第 11 部分**
- **1.5 简历怎么写**：格式 `动作 + 技术 + 可量化结果`，真实 bullet：
  - Hybrid 检索 + Cross-Encoder 精排，Precision@1 83.1% → **89.2%**（39 篇文档 / 65 条）
  - 意图识别规则 51% → **100%**（intent_v3 + 覆盖，100 条）
  - 无检索 20% 幻觉 → RAG + 自纠错 **0%**（同模型裁判）
  - 写操作 `pending_action` + 确认 token + 幂等指纹，模型无法绕过服务端权限
  - **红线**：数字必须带口径，引用 `eval/MEASURED.md`
- **1.6 高频追问接法**：各指向对应技术章
- **1.7 练习**：3 分钟录音自述 + 对照五段式自查

### 阶段一 · 打基础

**第 2 章 向量与相似度（第二部分 · 向量表示）**
- 概念：向量表示、余弦相似度、维度、归一化、为什么语义检索能召回字面不同的句子
- 本仓库：`app/providers/embeddings.py`（`BAAI/bge-small-zh-v1.5`）、`app/retrieval/vector.py`、`app/providers/device.py`
- 取舍：本地小模型 vs 在线大模型；维度与存储成本
- 反例：未归一化直接点积 → 相似度排序错乱
- 练习：手算两个 3 维向量的余弦相似度

**第 3 章 解析、清洗与切块（第三部分 · 索引构建）**
- 概念：文档解析、文本清洗、chunk 大小与重叠、按语义/标题切、chunk id 与来源元数据
- 本仓库：`app/retrieval/unstructured_parser.py`、`cleaning.py`、`chunking.py`、`ingest.py`
- 取舍：切太碎丢上下文，切太大稀释语义；重叠的存储代价
- 反例：按固定字符数硬切，把"退货政策"标题与正文切到两个 chunk
- 练习：给一篇政策文档，设计切块参数并说明理由

**第 4 章 BM25 与稠密召回（第四部分 · 召回）**
- 概念：稀疏召回（关键词、订单号、政策名）vs 稠密召回（口语化、同义改写）
- 本仓库：`app/retrieval/bm25.py`、`vector.py`、`tokenizer.py`
- 数据：BM25 76.9% vs bge-small 83.1%（P@1）
- 反例：只用向量检索，"ORD10001"被"语义化"后召回下降
- 练习：同一 query 分别用两种方式召回，对比差异

### 阶段二 · 提质量

**第 5 章 RRF 与 Hybrid 融合（第五部分 · 融合精排）**
- 概念：两路候选如何合并；RRF 用排名而非分数，规避分数量纲不一致
- 本仓库：`app/retrieval/fusion.py`、`hybrid.py`
- 取舍：为什么不用加权求和（BM25 分数无界、向量相似度有界，无法直接相加）
- 练习：手算两路 top-3 的 RRF 融合

**第 6 章 Cross-Encoder 精排（第五部分 · 融合精排）**
- 概念：召回是"粗筛"（快、准度低），精排是"精筛"（慢、准度高）；两阶段架构
- 本仓库：`app/retrieval/reranker.py`、`app/providers/reranker.py`（`BAAI/bge-reranker-base`）
- 数据：Hybrid + CE 89.2% / 97.7% / MRR 0.94
- 取舍：精排延迟代价，为什么只对 top-N 精排

**第 7 章 查询改写与自适应检索（第六部分 · 查询改写）**
- 概念：Query Rewrite、复杂度判定、检索不足时的自纠错
- 本仓库：`app/retrieval/query_rewrite.py`、`adaptive.py`、`self_rag.py`、`app/prompts/self_rag.py`
- 数据：无检索 20% 幻觉 → RAG + 自纠错 0%
- 取舍：多轮自检的延迟与 token 成本；路由误判（该检索却直接答 → 幻觉）

### 阶段三 · 管上下文

**第 8 章 上下文组织与引用注入（第七部分 · 上下文与记忆）**
- 概念：上下文窗口、Prompt 结构、检索片段转上下文、引用如何避免幻觉
- 本仓库：`app/prompts/answer.py`、`app/agents/nodes/generate.py`、`app/schemas/retrieval.py`（`Citation`）
- 取舍：塞更多上下文 vs 稀释注意力

**第 9 章 会话记忆与三级压缩（第七部分 · 上下文与记忆）**
- 概念：短期=当前会话消息；长期=摘要与压缩；三级压缩策略
- 本仓库：`app/memory/budget.py`、`compression.py`、`summarizer.py`、`app/agents/nodes/memory.py`
- 关键：`app/agents/state.py` 的 `AgentState` 注释——为什么不用 `Annotated[add]` 无限追加
- 取舍：压缩会丢信息，不压缩会爆 128k 预算

### 阶段四 · 做决策

**第 10 章 意图识别（第八部分 · 意图与路由）**
- 本仓库：`app/agents/nodes/intent.py`、`intent_overlay.py`、`app/prompts/intent.py`
- 数据：规则 51% → intent_v3 + 覆盖 **100%**（100 条）

**第 11 章 复杂度路由与五策略（第八部分 · 意图与路由）**
- 本仓库：`app/retrieval/adaptive.py`、`app/agents/nodes/router.py`、`app/agents/graph.py:38`（`_route_after_complexity`）
- 五策略：`DIRECT / SINGLE / MULTI / AGENT / REFUSE`（`app/core/enums.py`）
- 练习：给 5 句用户话术，判断应走哪条策略

**第 12 章 LangGraph 工作流与状态设计（第九部分 · 工作流与工具）**
- 本仓库：`app/agents/graph.py`、`state.py`、`app/agents/nodes/`
- 取舍：为什么用图而不是一个大函数；状态字段如何设计

**第 13 章 工具调用、权限与幂等（第九部分 · 工作流与工具）**
- 本仓库：`app/tools/registry.py`、`app/tools/permissions.py`、`app/agents/nodes/planner.py`、`executor.py`、`app/repositories/idempotency.py`
- 反例：让模型直接执行退款，被注入绕过

### 阶段五 · 控风险

**第 14 章 人工确认 HITL（第十部分 · 安全护栏）**
- 本仓库：`app/schemas/chat.py`（`ActionProposal`）、`app/services/`、`app/api/routes/chat.py`
- 取舍：为什么确认 token 必须服务端校验

**第 15 章 护栏与安全（第十部分 · 安全护栏）**
- 本仓库：`app/guardrails/injection.py`、`boundary.py`、`hallucination.py`、`app/agents/nodes/guardrail.py`
- 取舍：护栏必须在意图识别**之前**；Prompt 不是权限系统

### 阶段六 · 拿证据 · 上生产

**第 16 章 测评、指标口径与复现（第十一部分 · 评测体系）★ 独立成部分**
- **16.1 为什么测评是这类项目最硬的证据**：没有测评的 RAG 只能"演示"，不能"证明"
- **16.2 数据集构成**：意图 100 条；检索 65 条 / 39 篇文档；端到端关键词 9/11。锚点：`eval/dataset/`
- **16.3 指标定义与读法**：Precision@1 / Recall@3 / MRR / 幻觉率 / E2E P50·P95；MRR 为什么比单看 Accuracy 更能反映排序质量
- **16.4 消融实验**：BM25 76.9% → bge-small 83.1% → Hybrid+CE **89.2%**，逐项说明增益来源
- **16.5 幻觉率对比**：无检索 20% → RAG + Self-RAG 自纠错 **0%**（同模型裁判）
- **16.6 口径陷阱**：模型版本（`deepseek-chat`）、裁判模型、知识库版本、日期（2026-08-22）必须写全
- **16.7 怎么复现**：`pytest -q`、`python -m eval.runner --task retrieval`
- **16.8 练习**：跑一次 retrieval 评测，解释 MRR 相对 P@1 的变化
- 锚点：`eval/runner.py`、`eval/MEASURED.md`、`docs/14-evaluation-report.md`

**第 17 章 可靠性与降级（第十二部分 · 工程化与上线）**：`app/core/retry.py`、`app/infra/redis_client.py`；超时、退避、降级矩阵
**第 18 章 可观测性（第十二部分 · 工程化与上线）**：`app/observability/`；trace_id 贯穿、JSON 日志、Prometheus、`LatencyBreakdown`
**第 19 章 部署（第十二部分 · 工程化与上线）**：`docker-compose.yml`、`Dockerfile`、`app/asgi.py`；依赖降级矩阵、迁移与 seed 生命周期

### 附录

术语表（含五策略中英对照）、环境变量、练习答案、源码阅读顺序、**完整测评数据表**。

## 4. 每章统一模板

| 块 | 作用 | 硬性要求 |
|---|---|---|
| **概念要点** | 先讲技术本身 | 3–5 条，脱离本项目也能读懂 |
| **本仓库实现** | 落回代码 | 真实文件路径 + 行号，不贴整文件 |
| **为什么** | 取舍 | 必含至少一个反例："不这样做会怎样" |
| **练习** | 可验证 | 1–2 道动手题 + 答案 |
| **指标回指** | 评测贯穿 | 本技术对应第 16 章的哪个指标，贡献多少 |

**评测贯穿原则**：技术章结尾回指指标，让读者始终知道"这个技术在为哪个数字服务"；但**完整口径集中到第 16 章**，前面只做一句话回指，不展开。

## 5. 写作规范

1. **技术优先，项目佐证**：先讲通用原理，再落代码。
2. **循序渐进**：部分按六阶段推进；部分之内也由浅入深，不跳步。
3. **评测不突兀**：第 1 章只给指标引子，完整评测放第 16 章；技术章只用一句话回指。
4. **代码引用**：统一 `相对路径:行号`，例如 `app/agents/graph.py:38`。
5. **数字口径**：任何指标带模型版本、数据集规模、裁判模型、日期，引用 `eval/MEASURED.md`。
6. **术语一致**：五策略 `DIRECT/SINGLE/MULTI/AGENT/REFUSE` 全文统一。
7. **命名风格**：部分名用简短技术名词短语（2–6 字），如"向量表示""索引构建""评测体系"，不堆形容词。
8. **图**：技术原理用示意/流程（Mermaid 或 SVG），项目链路复用 `docs/17`。
9. **不夸大**：非目标写清（`docs/00` 1.7），避免"生产级""全自动"。

## 6. 推进节奏

| 里程碑 | 产出 | 验收标准 |
|---|---|---|
| M1 | 第 1 部分（第 1 章） | 读者能背 30 秒/3 分钟版，能写简历 bullet |

## 8. 一句话总结

**12 个部分按"基础 → 提质量 → 管上下文 → 做决策 → 控风险 → 拿证据/上生产"六个阶段循序渐进；部分名用简短技术名词（向量表示、索引构建、融合精排、评测体系……）；评测独立成部分但不前置，放在技术讲完之后作为验证环节。**
