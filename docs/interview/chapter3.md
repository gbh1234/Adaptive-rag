# Chapter 3 · 当系统开始行动：工具、记忆与可靠性

解释退货政策和真正取消订单，区别不在于回答有多流畅，而在于后者会改变外部世界。一个工具调用如果参数错了、权限漏了或超时后重试两次，后果不能靠更漂亮的提示词修复。本章讨论客服系统从「会回答」走向「能办事」时，运行时必须承担的约束。

我们从一次订单操作开始，依次看工具契约、人工确认、幂等、降级、记忆压缩和评测。最后把这些机制放回面试语境：能讲清失败边界，比堆叠框架名更有说服力。

> **本章对应面试维度**：工具管理、容错与鲁棒性、记忆与上下文、工程化踩坑、Agent Infra。逐题追问见 [Chapter 3 问题库](03-rerank-memory-skill-mcp.md) 和 [Chapter 1 问题库](01-langgraph-planning-intent.md)。

## 3.1 工具是有契约的动作接口

工具首先是一份明确的输入输出契约。[`Tool`](../../app/tools/base.py) 用 `input_model` 验证参数，并把异常转成系统能处理的工具错误；[`ToolRegistry`](../../app/tools/registry.py) 维护名称到实现的映射，同时暴露 Function Calling schema。模型可以提出 `get_order` 或 `cancel_order`，但工具是否存在、参数是否合法，最终由程序检查。

工具目录并非越大越好。用户问退货时，只需看到退货相关能力；问物流时，应优先看到订单跟踪能力。[`skills/definitions`](../../app/skills/definitions/) 存储退货、跟踪和推荐流程，[`match_skill`](../../app/skills/loader.py) 按触发词或意图选中一个 Skill，Planner 用它收窄可见工具。Skill 是一份任务说明与工具范围，Tool 才是实际执行接口。

MCP 位于另一层：[`app/mcp/adapter.py`](../../app/mcp/adapter.py) 把 MCP 端点适配为本地 Tool 接口，让注册和调用路径保持一致。Function Calling 是模型侧的结构化调用形式，MCP 是工具对接协议，Skill 是流程知识。三者可以组合，但不能混为同一个概念。本项目没有通用的百级工具搜索或 A2A 多 Agent 协议。

## 3.2 人工确认必须落实到执行条件

风险分层在 [`app/tools/permissions.py`](../../app/tools/permissions.py)。读操作可以直接执行；写操作或破坏性动作需要明确确认。Planner 扫描计划时，若发现需要确认的工具而当前请求没有 `confirm_action_id`，就产生 `pending_action`。Executor 看到未确认提案，本轮不会执行计划中的写动作；生成节点返回待确认说明。

```text
用户请求写操作 → Planner 提案 → 暂停执行 → 用户确认
                                          ↓
                             Executor 权限校验 → 工具执行
```

这使得「请用户确认」成为可检查的状态转换。单靠提示词让模型说一句「确认吗」并不够：只要执行器仍可调用写工具，模型输出就可能与实际动作脱节。反过来，确认标识也不是无限授权；工具名、参数和用户作用域仍需在执行时校验。

## 3.3 幂等处理重试造成的重复动作

写操作最难处理的是模糊失败：请求发出后超时，调用方不知道动作是否已经成功。如果机械重试，可能把一次退款变成两次。[`executor.py`](../../app/agents/nodes/executor.py) 对写工具构造工具名与参数的指纹，并用确认标识或幂等键查询 [`IdempotencyRepository`](../../app/repositories/idempotency.py)。相同键与指纹命中时复用先前结果；键相同而动作不同则报冲突。

这层设计能避免本服务中常见的重复提交，却仍有边界：外部支付或退款服务也必须提供可靠的幂等接口，数据库事务与外部系统之间仍可能存在部分成功的失败窗口。回答「如何保证只退一次」时，应该把本地去重和跨系统一致性分开说明。

## 3.4 降级要沿风险方向走

读工具失败可以尝试另一条读路径，例如查询订单失败后改为检索通用政策，让用户至少得到可用说明。[`READ_FALLBACKS`](../../app/agents/nodes/executor.py) 把这种替代关系写成固定表。权限拒绝不会进入降级表；写工具也不会因失败被换成另一种写动作。这条规则的本质是：**可用性下降时，权限不能自动扩大。**

模型服务的瞬时错误则由 [`retry.py`](../../app/core/retry.py) 处理：对超时和可重试 HTTP 状态做指数退避与 full jitter，避免多个实例同时重试；鉴权、无效请求等错误不靠重试解决。重试函数解决的是暂时性故障，不代替工具幂等，也不意味着所有流式输出都能无痕重放。

查询边界、注入检测和回答忠实度分别处理不同风险：前两者发生在输入与工具调用前，后者检查输出与证据。见 [`app/guardrails/`](../../app/guardrails/) 和 [安全手册](../09-security.md)。护栏可能误杀，也可能漏检；因此权限检查必须留在工具执行层。

## 3.5 记忆是预算管理，不是无限保存

会话要能接续，但每轮把所有历史、工具输出和文档片段无上限地塞给模型，会增加成本并污染上下文。[`budget.py`](../../app/memory/budget.py) 用字符长度估算 token，这不是官方 tokenizer；[`compression.py`](../../app/memory/compression.py) 按配置阈值压缩：约 50% 开始收紧工具结果，70% 缩旧轮次，85% 自动摘要，保留最近四轮。

压缩会损失信息。订单号、尺码、时间等实体如果从旧轮次被删掉，下一轮可能出现错误。因此记忆系统需要的不只是压缩率，还包括「关键实体能否被保留」的回归测试。目前仓库实现的是会话存储与摘要压缩，没有跨会话长期向量记忆，也没有实体保真度评测。

## 3.6 如何证明系统更可靠

[`eval/runner.py`](../../eval/runner.py) 把离线评测拆成意图、检索、生成、E2E；[`tests/`](../../tests/) 包括单元、集成和端到端测试。它们回答的问题不同：单元测试检查分支与契约，检索集检查证据排序，生成集检查回答质量，E2E 才接近用户路径。历史 E2E 仅 16 条，其延迟分位数不能作为生产 SLA。

项目已有 trace、日志、指标和限流，见 [`app/observability/`](../../app/observability/)；但没有 LangGraph 节点级 checkpointer、通用沙箱、Kubernetes 调度、模型微调或 GPU 推理平台。会话持久化也不能替代执行图的断点恢复。这些问题可以作为后续设计讨论，不能写成已经完成的工程成果。

## 面试时如何把三章串成一段话

> 我们先把客服请求分成直接回答、政策检索、工具操作和拒答等路径；检索路径用切块、双路召回、融合与精排提供证据，复杂问题再补一跳；工具路径让模型提出计划，但由执行器核验参数、权限和确认状态，并对写操作做幂等。生成后再检查答案与证据是否一致。离线评测显示检索与生成有所改善，但样本量和裁判方式限制了这些数字的外推范围。

这段叙述的顺序与系统真正的执行顺序一致。每说到一层，都能指出代码、失败例子和评测口径，面试官继续追问时就有落点。

## 本章小结

- Tool、Skill、MCP 处于不同层：执行契约、任务说明和接入协议。
- 写操作要在执行器里确认并去重；读操作才能按固定表降级。
- 上下文压缩节约预算，也可能损失关键实体。
- 测试和离线评测提供证据，但不自动变成生产 SLA。
