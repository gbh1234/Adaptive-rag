# Chapter 2 · 知识如何成为可核验的答案

「定制商品能不能七天无理由退？」这类问题看似只需从政策文档中找一句话，实际上包含四个连续判断：文档是否被正确解析，例外条件有没有在切块时丢失，检索是否找到相关证据，以及模型有没有把证据解释成超出原文的承诺。RAG 的质量取决于这条链路中最弱的一环。

本章从 `knowledge/` 里的文件出发，沿离线索引、在线召回、精排、多跳和生成检查追踪答案的形成。与其罗列算法名，不如问每个算法解决哪一种具体失败。

> **本章对应面试维度**：RAG 与检索、记忆与上下文、评估与全局观。逐题追问见 [Chapter 2 问题库](02-adaptive-rag-chunking-hybrid.md)。

## 2.1 第一条边界：文件不等于检索证据

`knowledge/` 包含 FAQ、退货、配送等 Markdown 政策。启动时，[`ingest.py`](../../app/retrieval/ingest.py) 读取并解析文件，经清洗、去重、切块、向量化后建立索引。文件名决定文档类目，类目不是模型自动分类的结果。当前知识库是启动时全量载入；改动文件后需要重新 ingest，不能称为热更新或增量删除。

切块是把长文档变成可定位的证据单元。[`chunking.py`](../../app/retrieval/chunking.py) 使用结构信息和窗口，并给 chunk 生成稳定 ID。稳定 ID 让同一证据能在检索结果、引用和评测中被追踪。切得过大，会把主题无关的规则一起送入上下文；切得过小，「七天」与「定制商品例外」可能分散到不同片段，模型只读到其中一半。因此，chunk 大小不只是性能参数，还决定了业务例外能否被完整表达。

```text
知识文件 → 解析/清洗 → 结构化切块 → 稳定 ID → BM25 与向量索引
```

生产解析可调用 Unstructured 处理多种文件；测试或缺少相关依赖时，Markdown 有简化路径。不同格式的解析质量并不相同，尤其不能把 PDF/图片支持直接等同于稳定 OCR 质量。具体路径与限制见 [解析与检索手册](../15-ingest-and-retrieval.md)。

## 2.2 第二条边界：用户措辞不等于索引措辞

用户可能说「买的耳机坏了怎么办」，文档标题写的是「电子产品售后与保修」。[`QueryRewriter`](../../app/retrieval/query_rewrite.py) 尝试把查询变成更适合检索的表述；模型失败时有回退。但改写也可能改变事实约束，所以系统仍需把原问题和检索结果一起交给后续生成与核对。

对单跳政策问题，[`retrieval_node`](../../app/agents/nodes/retrieval.py) 取改写后的第一条 query，运行 Hybrid 检索，再精排。对 `MULTI` 问题，节点调用 [`SelfRAGLoop`](../../app/retrieval/self_rag.py)：每一跳改写、检索、精排、判断证据是否足够；若不够，用 `missing_aspect` 指明下一跳缺什么。循环受 `max_retrieval_hops` 约束，而不是模型说继续就无限继续。

**例子**：用户问「定制商品过了七天还能退吗？」第一轮可能找到一般退货规则，证据评估发现缺「定制商品例外」，第二轮再针对该条件搜索。多跳的意义是补证据，不是把同一问题机械重复检索三次。多跳结果也会按 `chunk_id` 累积去重。

## 2.3 第三条边界：召回和排序承担不同职责

[`HybridRetriever`](../../app/retrieval/hybrid.py) 同时使用 BM25 和向量检索。BM25 对政策中的精确词、型号和规则名称敏感；向量路补同义表达与语义相近的问法。两路分数的量纲不同，[`fusion.py`](../../app/retrieval/fusion.py) 用 RRF 合并排名，而不是直接相加原始分数。一条路失败时，另一条路仍可返回结果；两路都没有结果才失败。

召回负责「不要漏」，精排负责「把最合适的放前面」。[`reranker.py`](../../app/retrieval/reranker.py) 可加载本地 Cross-Encoder 对候选重新评分。历史实测使用 `BAAI/bge-reranker-base`，不是 Cohere；权重未加载时的降级分数也不能称为 Cross-Encoder 结果。

历史 65 条检索样本提供了一个有意思的反例：BM25 的 P@1 为 **76.9%**，仅 bge-small 的 P@1 为 **83.1%**，两路 RRF 仍为 **83.1%**，Hybrid 加 Cross-Encoder 才到 **89.2%**。[实测记录](../../eval/MEASURED.md) 表明这轮增益主要来自精排；不能因为系统用了 RRF，就把全部提升归给融合。

## 2.4 第四条边界：找到文档不等于回答有依据

生成节点最多取前几条证据，连同工具结果和用户问题构造回答，并把模型给出的 `citation_chunk_ids` 映射为引用，见 [`generate.py`](../../app/agents/nodes/generate.py)。若模型调用失败，系统给出抽取式降级回答；若没有可靠证据，则请求更多信息或转人工。

回答生成后，[`faithfulness.py`](../../app/agents/nodes/faithfulness.py) 调用 LLM 校验是否被证据支持；不支持时尝试重写一次，再以抽取式回答兜底。这里的「忠实度」是模型判断，不是逻辑证明。校验器不可用时，[`hallucination.py`](../../app/guardrails/hallucination.py) 返回 `checker_unavailable`；因此不能说所有回答都获得强验证。

在流式路径中，模型 token 可以早于忠实度检查发给前端。事后修正最终答案时，用户可能已经看见旧片段。这是当前实现的真实权衡：更快的首字体验换来中途文本与最终答案可能不一致。讨论生产改进时，可以考虑缓冲待验证内容或把流式标为草稿，但这些不是当前已实现行为。

## 2.5 如何读懂检索指标

P@1 问「排第一的证据是否相关」，R@3 问「相关证据有没有进入前三」。生成的 Faithfulness 又是在问「回答是否能从证据推出」。三者不能互换。历史报告中的金标按文档 stem，生成评测使用同模型裁判，E2E 集仅 16 条；这些口径都决定了数字的解释范围。

| 历史离线阶段 | 结果 | 能说明什么 |
|---|---:|---|
| BM25 | P@1 76.9%，R@3 90.0% | 稀疏基线 |
| 仅 bge-small | P@1 83.1%，R@3 94.6% | 稠密路在该集较强 |
| Hybrid + CE | P@1 89.2%，R@3 97.7% | 融合后精排的最终检索路径 |
| RAG 生成 | Faithfulness 96.9% | 同模型裁判下的生成质量，非线上保证 |

数据来源：[eval/MEASURED.md](../../eval/MEASURED.md)。改知识库、切块方式或金标后，必须重新跑评测；旧数字不应自动继承。

## 本章小结

- 离线阶段决定证据粒度；在线阶段决定哪些证据进入上下文。
- Hybrid 是召回策略，RRF 是融合方法，Cross-Encoder 是候选精排；本轮数据要按各自贡献解释。
- 多跳只服务需要补证据的问题，并受轮次限制。
- 引用和忠实度检查提高可核验性，但无法把模型判断变成绝对保证。
