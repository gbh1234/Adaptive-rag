# Chapter 1 · 从一句客服提问到一张可控的执行图

用户说「你好」，系统应当立即回应；用户说「定制商品还能退吗」，系统需要查政策；用户说「帮我取消 ORD100001」，系统必须确认身份、读取订单，并在执行写操作前停下来等待确认。三个句子都进入同一个聊天接口，却要求三种不同的执行方式。这是本项目的第一个设计问题：**怎样让模型参与决策，同时让业务流程保持可解释和可约束？**

本章沿着一次请求走进 `ChatService` 和 LangGraph，解释意图、复杂度、规划与状态各自负责什么。读完后，你应该能不看图说清：请求为何进入某条分支，模型何时做决定，代码又在何处收回决定权。

> **本章对应面试维度**：架构选型、业务 AI 工程、Prompt 与框架原理、简历项目拷打。逐题追问见 [Chapter 1 问题库](01-langgraph-planning-intent.md)。

## 1.1 从业务差异推导执行路径

电商客服看似是问答，实际上混合了三类任务：纯对话、基于知识的解释、对业务系统的读写。若让所有问题都先检索，问候会平白增加延迟；若让所有问题都交给自由循环的 Agent，退款一类操作又会承担不可接受的执行风险。因此，本项目把「要不要检索或调工具」显式建模为路由结果。

```text
请求 → 护栏 → 意图识别 → 复杂度路由
                         ├─ DIRECT：问候等直接生成
                         ├─ SINGLE：单次政策检索
                         ├─ MULTI：迭代补齐政策证据
                         ├─ AGENT：规划并执行工具
                         └─ REFUSE：超出范围时拒答
```

这五种策略的分支写在 [`app/agents/graph.py`](../../app/agents/graph.py)，复杂度判断写在 [`app/retrieval/adaptive.py`](../../app/retrieval/adaptive.py)。护栏位于意图之前：已经判定为应拒答的请求不再交给后续模型分类。`SINGLE` 和 `MULTI` 进入同一个检索节点，但节点内部采用不同算法；`AGENT` 才进入 Planner 和 Executor。生成后，非拒答路径经过忠实度检查，再压缩会话。

**设计推论**：所谓「智能路由」不是多写几条 `if` 就结束。关键是每条路要有明确的输入、输出和失败行为。路由模型不可用时，规则回退会依据意图、订单号和复杂条件给出一个保守策略；这保证服务还能回答，但也意味着误分类可能影响后续分支，需要单独测量。

## 1.2 State 是节点间的共同语言

LangGraph 的节点不会互相调用内部函数，而是读取并更新 `AgentState`。状态里承载用户问题、意图、策略、检索片段、计划、工具结果、待确认动作和最终回答。这样设计的好处是：每一步的结果都可以被下一步检查，也便于单独测试节点。

图在 [`ChatService.__init__`](../../app/services/chat_service.py) 构建一次，而不是每个请求重新编译。请求开始时，`ChatService` 负责限流、读取会话并初始化状态；请求结束后，它把回答和摘要写回会话存储。数据库连接放在请求作用域中，工具通过 [`request_scope`](../../app/core/request_scope.py) 获取，不把连接对象塞进图状态。状态存储的是业务数据与决策结果，不应成为运行时资源的杂物箱。

> **面试追问：有图就等于自主 Agent 吗？** 不是。这个图大部分路径是有界工作流。只有 `AGENT` 路径包含模型规划工具步骤；工具观察不会在每一步回流给 Planner 重新规划。准确称呼是「带规划分支的客服工作流」。

## 1.3 两次模型判断：意图与复杂度

意图识别回答「用户想办什么」，复杂度路由回答「办这件事需要哪种路径」。这两个问题相近，却不能合并。比如「七天无理由怎么算」是政策解释；「这张订单还能七天无理由退吗」既包含政策，又可能需要订单数据。前者可走检索，后者应优先考虑工具。

[`IntentClassifier`](../../app/agents/nodes/intent.py) 使用结构化模型输出，并在失败时回退到规则；高混淆短语还经过覆盖层纠偏。[`AdaptiveRouter`](../../app/retrieval/adaptive.py) 根据意图与查询估计复杂度，输出五种策略之一。JSON 模式和低温度只是降低输出波动；[`json_parser.py`](../../app/providers/json_parser.py) 的 schema 校验才是程序接受决策的边界。

这里有一个容易被问穿的数字：历史自建 100 条样本上，`intent_v3` 加覆盖层达到 100%。这不是纯模型成绩，也不是线上分布的准确率。[实测记录](../../eval/MEASURED.md) 给出了各基线；面试时应同时说出样本来源、覆盖层和外推限制。

## 1.4 规划器只提出计划，执行器决定能否行动

进入 `AGENT` 路径后，[`Planner`](../../app/agents/nodes/planner.py) 按意图和匹配到的 Skill 给模型一份受限工具目录。模型返回结构化 `AgentPlan`；代码丢弃未知工具，并把计划截为最多六步。模型即使写出一个不存在的工具，也不会凭空获得执行能力。

[`Executor`](../../app/agents/nodes/executor.py) 再逐步执行计划，并检查调用次数与风险等级。读工具失败可以按固定表尝试替代读工具；写工具要经过人工确认和幂等校验。于是模型的工作是**提出候选步骤**，程序的工作是**验证并执行允许的步骤**。这种分工比宣称「模型自主完成退款」更能解释系统的真实边界。

当计划包含写操作且尚未收到确认时，Planner 生成 `pending_action`；Executor 本轮不执行工具，回答节点返回确认文案。下一轮带上确认标识后才进入写路径。确认并不是提示词里一句「请谨慎」，而是执行前可检查的状态条件。详见 [Chapter 3](chapter3.md)。

## 1.5 从一次请求看出架构边界

设用户输入「帮我取消 ORD100001」。理想路径是：护栏检查 → 识别取消订单意图 → 路由到 `AGENT` → Planner 提出读取订单、取消订单等步骤 → 写动作生成待确认提案 → 用户确认后 Executor 执行。真实结果还依赖订单状态、权限与工具返回，不能因为计划中出现 `cancel_order` 就说订单已取消。

这条路径也说明本项目没有实现什么：没有每步 ReAct 重规划，没有多 Agent 团队，没有 LangGraph 节点级 checkpointer。会话消息虽有持久化，但不等于执行图可以从任意节点恢复。面试官问到这些能力时，可以讨论适用场景和新增成本，不应把它们算作现有功能。

## 本章小结

- **判断层**：意图决定任务类型，复杂度决定执行策略。
- **编排层**：LangGraph 把分支和节点输出显式化；`ChatService` 负责请求生命周期。
- **执行层**：Planner 提议，Executor 校验，写操作等待确认。
- **证据边界**：离线意图成绩含覆盖层；单图工作流不能描述成多智能体系统。
