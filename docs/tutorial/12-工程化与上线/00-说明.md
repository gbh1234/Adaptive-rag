# 工程化与上线 · 说明

> 本部分是全书十二个部分中的第十二个，它属于第六阶段"拿证据与上生产"的收尾。前面十一个部分讲完了整套技术与验证方式，本部分讲的是最后一件事。

这件事就是：怎样让这套系统稳定地跑起来、出问题能被看见、换环境能被部署。

---

## 一、为什么把工程化与上线单独成部分

一个能跑通演示的系统，离一个能上线的系统，中间隔着一整套工程工作。演示只要求"正常情况下正确"，上线却要求"异常情况下不崩"。

外部依赖会抖动，网络会超时，模型会不可用，数据库会连接失败。系统必须在这些异常面前保持可用，至少保持优雅降级。

除了稳定性，上线还需要可观测性。当用户反馈"刚才那条回复不对"时，工程师必须能够顺着一条链路找到当时发生了什么。没有可观测性的系统，一旦出问题就只能靠猜。

> 本部分因此把稳定性、可观测性与部署放在一起讲，它们共同构成"从代码到线上服务"的最后一段路。

## 三、学习目标

读完本部分后，读者应当能够达成以下几个目标。

- 读者应当能够**说清哪些 HTTP 状态码应当重试、哪些不应当**，以及为什么。
- 读者应当能够**解释全抖动退避**为什么能避免重试风暴。
- 读者应当能够**说清 trace_id 如何贯穿**一条请求的全部环节。
- 读者应当能够**对照本项目的配置文件**，指出哪些依赖是硬依赖、哪些是软依赖。

---

## 四、使用建议

我们建议读者先读第一篇，理解系统如何面对异常，再读第二篇，理解系统如何暴露状态，最后读第三篇，理解系统如何被部署。

本部分有一条贯穿始终的原则，读者应当牢牢记住：**区分业务失败与系统失败**。

- 用户问了一个越界问题，系统拒答，这是**业务失败**，返回 200。
- 模型服务超时，系统无法作答，这是**系统失败**，返回 503。

> 把两者分开，是运维清晰的前提。

## 五、练习与自测

本部分的练习有两项。

- **第一项，判断重试。** 读者应说明 429 与 401 分别应当如何处理，为什么。
- **第二项，排障演练。** 读者应假设一条请求延迟偏高，说明如何用分段延迟与 trace_id 定位是哪一步慢。
