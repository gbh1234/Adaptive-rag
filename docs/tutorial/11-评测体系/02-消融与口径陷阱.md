# 消融与口径陷阱

> 本文是第十一部分的第二篇正文，它讲清消融实验与常见口径陷阱。全文分为五节，前两节讲意图与检索的消融，中间两节讲生成消融与端到端结果，最后一节给出口径陷阱与练习。

---

## 一、为什么要做消融

一个系统用了很多技术，最终成绩不错，但这并不能说明每一项技术都有效。可能其中某一项贡献很大，另一项贡献很小，甚至有一项根本没有贡献。

**消融实验（Ablation）** 的做法是：一次去掉一项技术，看成绩掉多少，从而分离出每一项的独立贡献。

> 它是把"技术清单"变成"增益来源"的唯一手段。

## 二、意图消融

意图识别的消融是一条清晰的链条，下表给出各版本的准确率。

| 配置 | 准确率 |
| --- | --- |
| 关键词规则基线 | 51% |
| v1（大模型，无覆盖层） | 85% |
| v2 | 86% |
| 仅覆盖层 | 100% |
| v3 加覆盖层（生产路径） | 100% |

关键词规则的基线准确率为 **51%**，这个数字说明纯规则远远不够。引入大模型之后，无覆盖层的 v1 版本达到 **85%**，v2 版本达到 **86%**，说明大模型把整体拉高了一大截。仅覆盖层单独作用为 **100%**，而生产路径的 v3 加覆盖层同样为 **100%**。

这组数字要连起来读。规则基线在"闲聊"与"商品咨询"两类上几乎为零，在"退款"上只有 **16.7%**，因为关键词分不清"退货"与"退款到账"。大模型补上了大部分差距，覆盖层则补上了最后那段由稳定中文歧义造成的差距。

> 读者在面试中必须主动说明：这个 100% 包含覆盖层，它不是纯模型判断。

## 三、检索消融

检索的消融是一条四行的对照表，它们来自同一次测量，使用同一个 65 条评测集。

| 配置 | Precision@1 | Recall@3 | MRR |
| --- | --- | --- | --- |
| BM25 | 76.9% | 90.0% | 0.84 |
| 仅 `bge-small-zh-v1.5` | 83.1% | 94.6% | 0.89 |
| BM25 + 向量 + RRF | 83.1% | 94.6% | 未报 |
| Hybrid + Cross-Encoder | 89.2% | 97.7% | 0.94 |

第一行是 **BM25**，它的 Precision@1 为 **76.9%**，Recall@3 为 **90.0%**，MRR 为 **0.84**。这是关键词召回的能力基线。

第二行是**仅使用 `bge-small-zh-v1.5`**，它的 Precision@1 为 **83.1%**，Recall@3 为 **94.6%**，MRR 为 **0.89**。相对 BM25，Precision@1 提升了 6.2 个百分点，Recall@3 提升了 4.6 个百分点。这说明语义召回确实补上了关键词召回覆盖不足的部分。

第三行是 **BM25 加向量再加 RRF**，它的成绩与仅向量**完全相同**，都是 **83.1%** 与 **94.6%**。这一点必须主动说明：在本评测集上，RRF 融合没有带来额外增益。很多人会想当然地认为"融合一定涨点"，实测否定了这个想法。

第四行是 **Hybrid 加 Cross-Encoder**，它的 Precision@1 为 **89.2%**，Recall@3 为 **97.7%**，MRR 为 **0.94**。相对 BM25，Precision@1 提升了 12.3 个百分点，Recall@3 提升了 7.7 个百分点。相对第三行的融合结果，Precision@1 提升了约 6.1 个百分点。

> 这四行连起来读，结论很清楚：真正带来增益的是 Cross-Encoder 精排，而不是融合。读者在简历与面试中，应当把 89.2% 这个数字归功于精排，而不是归功于 Hybrid 融合。

`eval/runner.py` —— `eval_retrieval` 中的 `_run`

```python
    async def _run(name: str, retrieve) -> dict:
        precs1, recalls3, hits1, hits3, mrrs = [], [], [], [], []
        for row in rows:
            chunks = await retrieve(row["query"])
            stems = _unique_stems(chunks)
            relevant = set(row["relevant_doc_ids"])
            precs1.append(precision_at_k(relevant, stems, 1))
            recalls3.append(recall_at_k(relevant, stems, 3))
            hits1.append(hit_at_k(relevant, stems, 1))
            hits3.append(hit_at_k(relevant, stems, 3))
            mrrs.append(mrr(relevant, stems))
        return {
            "backend": name,
            "n": len(rows),
            "precision_at_1": _summarize_scores(precs1),
            "recall_at_3": _summarize_scores(recalls3),
            "hit_at_1": _summarize_scores(hits1),
            "hit_at_3": _summarize_scores(hits3),
            "mrr": _summarize_scores(mrrs),
        }
```

`_run` 接收一个 `retrieve` 回调与一个系统名，对同一批评测集逐条取结果，并用 `_unique_stems` 把切片归并到文档级，从而保证评的是文档级召回。它把每个系统的 Precision@1、Recall@3、Hit@1、Hit@3 与 MRR 分别累计后，交给 `_summarize_scores` 汇总成一张对照表，消融的四行数据正是这样逐行跑出来的。

## 四、生成消融与端到端结果

### 4.1 生成消融

生成的消融有三行，下表给出三档配置的表现。

| 配置 | 忠实度 | 幻觉率 | 关键词命中 |
| --- | --- | --- | --- |
| 无检索 | 80% | 20% | 36.9% |
| 加 RAG | 96.9% | 3.1% | 95.4% |
| 再叠加自纠错 | 100% | 0% | 95.4% |

无检索时，忠实度为 **80%**，幻觉率为 **20%**，关键词命中为 **36.9%**。加入 RAG 后，忠实度升到 **96.9%**，幻觉率降到 **3.1%**，关键词命中升到 **95.4%**。再叠加自纠错后，忠实度达到 **100%**，幻觉率降到 **0%**，关键词命中保持在 **95.4%**。

这组数字说明两件事。第一件是检索本身是压制幻觉的主力：无检索到有检索，幻觉率从 20% 骤降到 3.1%。第二件是自纠错是最后的把关：它把幻觉率从 3.1% 压到 0%，但它**没有**提高关键词命中，因为它修的是"证据支撑"，不是"补全标准答案的词"。

### 4.2 端到端结果

端到端有 16 条用例，它们走完整的服务链路。拒答准确率为 **100%**，工具路径准确率为 **100%**，关键词命中为 **9 比 11**，即 **81.8%**，延迟的 P50 为 **4.9 秒**，P95 为 **5.8 秒**。

这组数字里有几处需要说明。关键词命中是 9 比 11，不是 11 比 11，读者不能把它写成 100%。延迟的分段数据显示，意图分段的中位延迟约 **803 毫秒**，生成分段约 **1084 毫秒**，而检索与工具分段的中位数为 **0**，这是因为 16 条里有相当一部分走的是直接回答或拒答，不检索也不调工具，中位数被拉平了。

实际最慢的是 `e02` 多跳用例，约 **11.1 秒**；注入用例 `e10` 仅约 **10 毫秒**，因为正则拦下后连大模型都没调用。

## 五、口径陷阱与练习

本部分列出四个必须主动说明的口径陷阱，下表先给出对照。

| 陷阱 | 错误读法 | 正确口径 |
| --- | --- | --- |
| 区间当提升 | 63 到 91 是提升 | 它是样本取值区间 |
| 降级当能力 | 哈希向量命中约 3% | 仅测试与无权重开发 |
| 模型名写错 | `bge-m3`、Cohere | `bge-small-zh-v1.5`、`bge-reranker-base` |
| 同模型裁判当人工 | 人工核查零幻觉 | 同模型裁判，偏乐观 |

第一个陷阱是**把置信区间误读为提升幅度**。BM25 的 Recall@3 为 **90.0%**，其后括号里的 **63 到 91** 是该指标在样本上的取值区间，不是提升前后的两个点。把区间当成提升，是简历里最常见的错误。

`eval/runner.py` —— `_summarize_scores`

```python
def _summarize_scores(values: list[float]) -> dict:
    if not values:
        return {"mean": 0.0, "min": 0.0, "max": 0.0}
    return {
        "mean": round(sum(values) / len(values), 4),
        "min": round(min(values), 4),
        "max": round(max(values), 4),
    }
```

`_summarize_scores` 对一组指标同时给出 `mean`、`min` 与 `max` 三个值，报告里每个指标后的括号正是 `min` 与 `max` 构成的取值区间。它提醒读者：括号里的是同一次测量在样本上的分布范围，而不是提升前后的两个点。

第二个陷阱是**把降级路径当作能力证明**。哈希向量的命中率只有约 **3%**，它只用于测试与无权重开发，绝不能写进简历；同样，词面重叠的降级重排也不是 Cross-Encoder。

第三个陷阱是**把模型名写错**。本项目的稠密模型是 `bge-small-zh-v1.5`，不是 `bge-m3`；精排模型是 `bge-reranker-base`，不是 Cohere。

第四个陷阱是**把同模型裁判当成人工核查**。忠实度 **100%** 是在同模型裁判下测得的，裁判与生成器共享知识与措辞，偏乐观。读者不应当把它说成"人工事实核查零幻觉"。

本部分的练习有两项。

- **第一项，分离增益。** 读者应说明 Hybrid 加精排相对 BM25 的提升来自哪一步，为什么。
- **第二项，排查陷阱。** 读者应检查一份简历，找出其中把区间误读为提升、或把降级路径当作能力的地方。

> **指标回指。** 本篇是全书证据链的收束。读者读完本篇，就掌握了本项目所有可验证的结论，以及每一条结论应当如何被正确引用。
