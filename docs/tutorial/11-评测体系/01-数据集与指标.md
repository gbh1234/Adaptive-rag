## 一、四类评测任务

本项目把可验证的能力钉在四类离线任务上，每一类回答一个问题。

第一类是**意图识别**，它回答"14 类意图能不能分对，覆盖层贡献了多少"。它使用 `eval/dataset/intent_100.jsonl`，共 100 条，金标是意图标签。

第二类是**检索**，它回答"政策文档能不能排到前面"。它使用 `eval/dataset/rag_eval.jsonl`，共 65 条政策问句，金标是相关文档的标识。

第三类是**生成**，它回答"有无证据时会不会胡编，自纠错有没有用"。它复用检索的 65 条，金标是答案应当包含的关键词。

第四类是**端到端**，它回答"注入会不会拒、订单会不会走工具、延迟多少"。它使用 `eval/dataset/e2e_eval.jsonl`，共 16 条。

> 这四类任务的分工很清晰：前两类评检索能力，第三类评生成能力，第四类评整条链路的综合行为。

## 二、数据集构成

### 2.1 意图集

意图集有 100 条，覆盖 14 个类别。类别的分布并不均匀，下表按数量分档给出。

| 类别 | 条数 |
| --- | --- |
| 政策问答 | 16 |
| 退货换货、越界 | 各 8 |
| 查单、物流、商品咨询 | 各 7 |
| 闲聊、退款、取消、推荐、优惠券、投诉、转人工 | 各 6 |
| 问候 | 5 |

这种分布反映了真实客服场景里各类问题的相对比例。

### 2.2 检索集与知识库

检索集有 65 条政策问句，金标是**文档名**而不是切片标识，例如 `return_policy`。

这一点很关键：评测评的是文档级召回，同一篇政策的多个切片只计一次。这 65 条覆盖 38 个不同的文档名，其中 5 条查询标了两篇相关文档，例如"包邮加优惠券"这类跨文档问题。

知识库 `knowledge/` 共 39 篇 Markdown，入库后约 156 个切片。

### 2.3 端到端集

端到端集有 16 条，它覆盖了五组场景。

| 场景 | 条数 |
| --- | --- |
| 问候 | 1 |
| 政策 | 6 |
| 工具 | 5 |
| 拒答 | 3 |
| 转人工 | 1 |

这些用例走完整的服务链路，包含护栏、意图、路由、工具与人工确认。其中 `e10` 是一条注入用例，期望系统拒答。

## 三、指标定义

### 3.1 检索指标

四个检索指标各衡量一件事，下表先给出总览。

| 指标 | 衡量什么 | 公式 |
| --- | --- | --- |
| Precision@1 | 第一条是否相关 | 前 1 条相关数 / 1 |
| Recall@3 | 证据是否进上下文 | 前 3 条命中数 / 金标数 |
| MRR | 首个相关的排名 | 首个相关排名取倒数 |
| Hit@k | 前 k 条是否有相关 | 二值 |

**Precision@1** 衡量排在第一位的文档是否相关，公式是"前 1 条里相关文档数除以 1"。这个指标对客服最敏感，因为用户最先看到的就是第一条依据。

**Recall@3** 衡量前三条里有没有覆盖到全部相关文档，公式是"前 3 条命中的相关文档数除以金标文档数"。这个指标衡量的是"证据有没有进上下文"，因为系统通常只把前几条切片交给模型。

**MRR** 是平均倒数排名，它取第一个相关文档排名的倒数。如果第一篇就命中，得分为 1；如果第二篇才命中，得分为 0.5；如果都没命中，得分为 0。

> MRR 比单看准确率更能反映排序质量，因为它对"第一篇是不是对的"很敏感。

**Hit@k** 衡量前 k 条里是否至少有一篇相关，它是一个二值指标，主要用于对照。

`eval/metrics.py` —— `precision_at_k`、`recall_at_k`、`hit_at_k`、`mrr`

```python
def precision_at_k(relevant: set[str], retrieved: list[str], k: int) -> float:
    top = retrieved[:k]
    if not top:
        return 0.0
    return sum(item in relevant for item in top) / len(top)


def recall_at_k(relevant: set[str], retrieved: list[str], k: int) -> float:
    if not relevant:
        return 0.0
    return sum(item in relevant for item in retrieved[:k]) / len(relevant)


def hit_at_k(relevant: set[str], retrieved: list[str], k: int) -> float:
    return 1.0 if any(item in relevant for item in retrieved[:k]) else 0.0


def mrr(relevant: set[str], retrieved: list[str]) -> float:
    for rank, item in enumerate(retrieved, start=1):
        if item in relevant:
            return 1.0 / rank
    return 0.0
```

`precision_at_k` 先截取前 `k` 条，用 `sum(item in relevant for item in top)` 统计命中数，再除以实际返回条数；`recall_at_k` 的分母换成金标集合的大小，因此它衡量的是覆盖率而不是排序精度。`mrr` 在遍历结果时一旦遇到相关项就返回排名的倒数，`enumerate(..., start=1)` 保证第一篇命中时返回 1.0。

### 3.2 生成指标

**Faithfulness（忠实度）** 是答案被证据支撑的比例，它由裁判模型判断。**幻觉率**是忠实度判负的比例，二者互补。

这里有一条必须说明的口径：本项目的裁判与生成器是同一个模型，同模型裁判偏乐观，因此幻觉率应当与关键词命中率并列报出，而不是单独强调。

**关键词命中**衡量标准答案应当包含的关键词是否全部出现在生成答案里。它比同模型裁判更独立，是生成质量的另一个视角。

### 3.3 端到端指标

端到端评测报告拒答准确率、关键词命中率、工具路径准确率与延迟。延迟用 P50 与 P95 两个分位，它们比平均值更能反映用户体感。

> 这里有一条关于小样本的提醒：本项目的端到端集只有 16 条，P95 是离散分位，它的数值受样本量影响较大，读者不应当把它当成稳定的线上分位。

## 四、指标怎么读

读指标时要连着条件读。同一个百分比，在不同数据集、不同裁判、不同日期下含义完全不同。

本项目的所有数字都来自同一次测量：日期为 **2026 年 8 月 22 日**，生成与裁判模型为 `deepseek-chat`，稠密召回为 `bge-small-zh-v1.5`，精排为 `bge-reranker-base`。任何一次引用，都应当带上这组条件。

还有一条读法上的提醒：不要只看一个指标。

- **检索要看 Precision@1 与 Recall@3 两个**，前者看"第一篇对不对"，后者看"证据全不全"。
- **生成要看忠实度与关键词两个**，前者看"有没有依据"，后者看"有没有说到点子上"。
