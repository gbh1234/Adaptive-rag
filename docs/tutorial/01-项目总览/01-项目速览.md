## 一、项目要解决的问题

### 1.1 传统客服 RAG 的单一链路

传统的客服机器人通常只实现一条链路：用户提问，系统做一次向量检索，再把检索到的内容交给大模型生成回答。

这条链路可以概括为**"检索一次，回答一次"**。它在标准问答上表现尚可，一旦放进真实的电商客服场景，很快就会暴露不足。

### 1.2 四类问题，四种代价

这套单一链路之所以失效，是因为电商客服面对的问题并不属于同一类型。按处理方式与风险，我们可以把它们归纳为四类。

| 类型 | 典型问题 | 依赖 | 错误代价 |
| --- | --- | --- | --- |
| 常识与政策问答 | 优惠券能否与会员折扣叠加 | 知识库检索 | 低，但需给出引用并核查事实 |
| 订单查询 | 我的订单现在到哪了 | 订单数据库 + 物流工具 | 中，需校验归属、防止越权 |
| 复杂售后 | 定制商品超七天但有质量问题能否退货 | 多条政策组合 + 多步推理 | 中高 |
| 业务写操作 | 取消尚未发货的订单 | 业务系统写接口 | 高，不可逆，需人工确认 |

这四类问题都来自自然语言输入，却在**延迟容忍度、检索需求、错误代价**上差异很大。

简单问题希望即时回答；复杂问题需要更多检索与推理预算；写操作一旦执行错误，后果不可逆。

### 1.3 单一链路的三个缺陷

如果系统把所有问题都交给同一条检索链路，就会带来三个结构性问题。

**其一，延迟浪费。** 哪怕是简单的政策问答，系统也会让它完整地走完检索与精排，而精排本身有计算成本。本可以快速返回的问题被人为拖慢。

**其二，召回不稳。** 订单号、政策名称这类精确词更适合关键词检索，口语化表达与同义改写更适合语义检索。系统只依赖向量时，精确词会在向量化中被"语义化"，召回反而变差；只依赖关键词时，口语化的问题又难以命中。

**其三，风险不可控。** 如果系统让模型直接决定并执行退款、取消这类写操作，那么一旦模型被提示注入或理解偏差影响，它就会在无人把关的情况下修改业务数据。

> 三个缺陷指向同一个结论：问题的处理成本与错误代价并不一致，因此系统不能采用一条固定链路处理全部请求。

## 二、项目的处理思路

针对上述问题，本项目采用的核心思路可以概括为**"先判断，再分流"**。

这一思路类似医院的分诊台：患者进门后并不会被直接送往某个科室，而是先由分诊台判断病情轻重，再决定送往急诊、普通门诊还是专科。本项目对请求的处理也是如此。

### 2.1 复杂度路由：五条路径

请求进入系统后，先经过安全护栏，随后进行意图识别与复杂度判断，再根据判断结果在五条路径中选择一条。前四条是正常处理路径，第五条是兜底。

| 路径 | 适用场景 | 处理方式 |
| --- | --- | --- |
| **Direct** | 可以直接回答的问题 | 不经过检索，延迟最低 |
| **Single** | 一次检索即可回答的问题 | 单路混合检索 |
| **Multi** | 需要多路检索、组合多条依据 | 多路检索 + 组合 |
| **Agent** | 需要调用外部工具的请求 | 进入计划与工具执行流程 |
| **Refuse** | 越界或无法处理的请求 | 明确拒答，不勉强生成 |

> 这五条路径让简单问题不消耗检索资源，也让复杂问题获得更多的检索与推理预算。

### 2.2 检索层：混合检索与精排

在检索层，系统同时维护 **BM25** 与**向量**两路索引。BM25 负责精确词汇的召回，向量检索负责语义相近内容的召回。

系统让两路结果通过 **RRF（Reciprocal Rank Fusion）** 融合为一个候选列表，再把它交给 **Cross-Encoder** 进行精排。这样，系统既保留了关键词检索在精确匹配上的优势，也保留了语义检索在表达多样性上的优势。

系统之所以不直接使用加权求和来合并两路结果，是因为 BM25 的分数没有固定上界，而向量相似度被限制在一定区间内，两者的量纲并不一致，无法直接相加。RRF 转而使用**排名**而非分数进行融合，它由此规避了这一问题。

### 2.3 动作层：回答与执行分离

在动作层，系统把"回答问题"和"执行动作"严格分开。

查询订单属于只读操作，退款、取消、修改地址属于写操作。模型只能**提出动作提案**，系统在真正执行之前还要对它进行服务端的参数校验、权限检查、幂等校验和用户确认。当确认令牌不匹配时，系统不会执行写操作。

> 这一层的存在，是区分本项目和普通问答演示的关键。普通演示往往止于生成一段文字，而本项目把重点之一放在了让模型的动作受到服务端规则的约束上。

## 三、项目的实测结果

项目在四类离线任务上做了测量。这些数据来自 `eval/MEASURED.md`，测量日期为 2026 年 8 月 22 日，生成与裁判模型均为 DeepSeek 的 `deepseek-chat`。下表给出整体印象，逐项口径见其后三小节。

| 任务 | 指标 | 结果 |
| --- | --- | --- |
| 意图识别 | 准确率（100 条测试集） | 51% → **100%**（含覆盖层） |
| 检索 | Precision@1 | 76.9% → 83.1% → **89.2%** |
| 检索 | Recall@3 | 90.0% → **97.7%** |
| 生成 | 幻觉率 | 20% → 3.1% → **0%** |
| 端到端 | 关键词命中 | **9 / 11** |
| 端到端 | P50 / P95 延迟 | **4.9 秒 / 5.8 秒** |

### 3.1 意图识别

关键词规则的基线为 **51%**。在引入 intent_v3 与歧义覆盖层之后，系统在 100 条测试集上的准确率达到 **100%**。

需要说明的是，该结果**包含覆盖层**，它并非纯模型判断，覆盖层主要负责对高混淆短语的纠偏。

### 3.2 检索

BM25 的 Precision@1 为 **76.9%**；系统仅使用 `bge-small-zh-v1.5` 时把它提升到 **83.1%**；再叠加 Cross-Encoder 精排后达到 **89.2%**。Recall@3 相应地从 **90.0%** 提升到 **97.7%**。

这组数字说明，向量召回解决了关键词检索覆盖不足的问题，而 Cross-Encoder 进一步提升了排序质量。

### 3.3 生成与端到端

在生成上，无检索时的幻觉率为 **20%**，系统加入检索后把它降到 **3.1%**，再配合 Self-RAG 自纠错，在同模型裁判下把它降到 **0%**。

在端到端任务上，十六个用例的关键词命中为 **9/11**，P50 延迟约 **4.9 秒**，P95 延迟约 **5.8 秒**。

> 这些数字的完整口径、数据集构成与复现方式，集中记录在第 11 部分"评测体系"。本文只用来建立整体印象。
